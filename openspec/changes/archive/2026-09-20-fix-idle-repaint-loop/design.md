## Context

Мотивация - в proposal.md («Why»), требования - в `specs/idle-power/spec.md`.
Здесь - как найдена причина, чем её чинить, чем закрепить и почему замер этого
требования сам по себе ненадёжен.

Приложение - `ApplicationWindow` (`src/qml/Main.qml`) с панелью инструментов в
`header`, холстом `DocumentCanvas` и панелью оглавления. Кадры выдаёт цикл
рендера Qt Quick: он рисует тогда и только тогда, когда сцена помечена грязной.
Непрерывные кадры в простое означают, что что-то помечает сцену грязной каждый
кадр и не приходит к устойчивому состоянию.

### Методика замера, и почему она важнее обычного

Первый разбор этого изменения дал **неверный ответ** (назвал причиной раскладку
в попапе настроек пера) - не из-за плохой гипотезы, а из-за четырёх ловушек
замера. Все четыре дают ложный ноль, то есть выглядят как «починено».

1. **pid подоболочки.** `cd "$D" && ./build/src/uq-notes ... &` уводит в фон
   составной оператор, и `$!` - pid подоболочки, а не приложения. У него расход
   нулевой всегда. Запускать надо напрямую: `cd "$D"; ./build/src/uq-notes ... &`.
2. **Зависшие процессы.** `kill` по неверному pid не убивает приложение. Два
   экземпляра прожили полтора часа, накопив по пять минут CPU; `pgrep` отдавал
   их вместо нового. Контроль - число потоков: у работающего окна их около 17,
   у осиротевшего без вывода на экран - 3.
3. **Окно не выведено на экран.** Пока экран погашен или окно не показано,
   композитор не шлёт frame callbacks, цикл рендера стоит, и **любой** вариант
   даёт 0%. Замер годен, только когда окно реально на экране.
4. **`UQ_FRAME_LOG` меняет то, что измеряет.** Эта переменная делает сводку
   кадров видимой, а сводка - один из двух источников петли. Считать ею кадры в
   простое нельзя: она создаёт ровно то, о чём сообщает.

Рабочий замер: запустить приложение напрямую, взять его собственный pid,
убедиться, что потоков ~17, дать 8 секунд на прогрев и взять прирост
`utime+stime` из `/proc/PID/stat` за 6 секунд. Без `UQ_FRAME_LOG`.

### Как найдена причина

Бисекция по `src/qml/Main.qml` на копии дерева (`RelWithDebInfo`, тот же
документ, замер по методике выше, без единого события ввода):

| Вариант | CPU в простое |
| --- | --- |
| пустое окно Qt Quick (контроль, вне приложения) | 0% |
| HEAD как есть, пять прогонов | 24.6 / 25.6 / 27.3 / 29.0 / 35.0% |
| только `DocumentCanvas`, без обвязки | 0% |
| без панели инструментов (`header`) | 26.8% |
| без панели оглавления | 26.1% |
| без трёх диалогов | 27.3% |
| без баннера ошибки | 30.5% |
| без тоста | 27.8% |
| без `FrameStats.window` | 22.1% |
| без сводки кадров (HUD) | 21.6% |
| без индикатора экспорта | 28.6% |
| **без сводки кадров И без индикатора экспорта** | **0% (дважды)** |
| то же на исходном `Main.qml` из HEAD | 0% |

Ключ к таблице - предпоследние строки. Поодиночке не помогает ничего, вместе -
помогает: источника два, и каждый самостоятельно держит окно грязным. Поэтому
одиночные вырезания и давали «всё те же 25%», что при первом разборе увело в
сторону.

**Сводка кадров** (`Main.qml:925`): `FrameStats` испускает `statsChanged` на
каждом кадре; текст сводки пересобирается, меняется `implicitWidth`, за ним -
ширина прямоугольника, сцена грязная, выдаётся кадр, снова `statsChanged`.
Прямоугольник при этом невидим (`visible: frameStats.logging`), но привязки
внутри невидимого элемента вычисляются как обычно.

**Индикатор экспорта** (`Main.qml:887`): петлю даёт сам контрол `ProgressBar`.
Проверено, что дело не в привязках: без `Layout.fillWidth` - 22.1%, с
постоянным `value: 0.5` - 23.5%. Достаточно убрать один `ProgressBar`, оставив
прямоугольник и подпись, - 0%.

Причина - в системном стиле, а не в нашем коде. В
`/usr/lib/qt6/qml/org/kde/breeze/ProgressBar.qml` заготовка для неопределённого
режима держит бесконечную анимацию, запущенную безусловно:

```qml
NumberAnimation on x {
    loops: Animation.Infinite
    running: true          // а не `running: control.indeterminate`
}
```

Бесконечная анимация помечает сцену грязной каждый кадр, сколько бы ни было
`indeterminate: false` и виден ли вообще контрол. Сопутствующий шум в выводе -
`TypeError: Cannot read property 'top' of null` дважды на кадр - оттуда же:
делегаты `Repeater` анкерятся к `parent.top`/`parent.bottom`, а модель
пересчитывается от меняющейся ширины. Стиль в проекте не задаётся, берётся
системный, так что на машине с Breeze это получает каждый пользователь.

Раскладка в попапе настроек пера (`ColumnLayout { anchors.fill: parent }`,
`Main.qml:236`) **невиновна**: на исходном коде из HEAD, с этой раскладкой на
месте, достаточно убрать два блока выше, чтобы получить 0%.

## Goals / Non-Goals

**Goals:**

- Убрать оба источника так, чтобы ни сводка кадров, ни индикатор экспорта не
  изменились в том режиме, ради которого существуют.
- Закрыть класс ошибки, а не два её вхождения: живой невидимой машерии в окне
  быть не должно, и это должно проверяться.
- Оставить после себя методику замера, на которой следующий разбор не
  споткнётся о те же четыре ловушки.

**Non-Goals:**

- Общая оптимизация кадра под нагрузкой: бюджеты `canvas-view` и `ink-input`
  выполняются и этим изменением не затрагиваются.
- Исправление самого стиля Breeze: причина найдена и названа, но чинится она в
  чужом репозитории и своим сроком.
- Проверка остальных контролов Breeze на ту же ошибку: после правки замер
  простоя даёт ноль, значит больше ни один из используемых не затронут.
- Правка раскладки в попапе настроек пера: к простою она отношения не имеет.

## Decisions

### D1. Невидимая машинерия не создаётся, а не прячется

Оба источника переводятся с `visible: <условие>` на
`Loader { active: <условие> }` с тем же условием. Пока условие ложно, внутри
`Loader` нет ни элементов, ни привязок - пересчитывать нечего, и петля
невозможна по построению, независимо от того, какой контрол окажется внутри
завтра.

Условия остаются прежними: `frameStats.logging` для сводки, `exporter.busy` для
индикатора. Новых ручек у пользователя не появляется.

Альтернативы:

- *Ограничиться заменой `ProgressBar` полосой на `Rectangle`.* Чинит один
  случай и ничего не говорит о следующем: сводка кадров петлит по совершенно
  другой причине и осталась бы. Отвергнуто как замена `Loader`; как дополнение
  к нему - принято отдельно (D5), но по другому поводу.
- *Оставить элементы, но обнулить привязки, пока невидимы.* Требует ручной
  дисциплины в каждом новом месте - ровно то, что уже не сработало. Отвергнуто.

### D2. Регрессию закрывают два теста, а не один

Проверять требование одним тестом не получается: под `QT_QPA_PLATFORM=offscreen`
цикл рендера крутится вхолостую **всегда**. Измерено на чистом дереве: за 2
секунды `frameSwapped=183`, `beforeSynchronizing=183`, `afterAnimating=183`,
`beforeRendering=183` - при 0% CPU (пустые свопы без реальной отрисовки). На
wayland то же дерево даёт ровно 0. Ни один сигнал окна под offscreen не отличает
покой от петли, и снимок геометрии всего дерева элементов тоже не отличает:
раскладка сходится по значению, грязной остаётся сцена.

Поэтому:

- **`tst_idlepower`** - структурный, идёт в обычном `ctest` под offscreen.
  Проверяет то, что от offscreen не зависит: пока условие ложно, у `Loader`
  нет `item`; `FrameStats` не испускает `statsChanged` без запрошенного замера.
  Это прямая проверка D1 и D3 и, через них, класса ошибки.
- **`tst_idleframes`** - на реальной платформе, проверяет само требование:
  после устаканивания за 1.5 секунды не выдано ни одного кадра. Регистрируется
  отдельно, без навязанного `QT_QPA_PLATFORM=offscreen`. Перед замером -
  канарейка: принудительно вызвать перерисовку и убедиться, что кадры вообще
  наблюдаемы; если нет (offscreen, погашенный экран, окно не выведено) -
  `QSKIP`, а не зелёный. Без канарейки тест проходил бы вхолостую именно в тех
  условиях, в которых он бесполезен, - это ловушка 3 из раздела о методике.

Это осознанный отход от инварианта «тесты не открывают окон»
(`tests/CMakeLists.txt`): один тест из набора его нарушает, потому что иначе
требование непроверяемо вовсе. Инвариант сохраняется для всех остальных.

Альтернатива - ограничиться структурным тестом. Дешевле, но он не заметит
третий источник, если тот окажется не `Loader`-ом. Отвергнуто: именно такой
«третий источник» и был пропущен при первом разборе.

### D3. `FrameStats` не будит интерфейс, пока сводка не запрошена

`statsChanged` испускается на каждом кадре только когда замер запрошен
(`logging == true`, то есть задана `UQ_FRAME_LOG`); иначе не испускается вовсе.
Сбор показателей на потоке рендера не трогаем - он дешёвый и нужен `markInput()`
из `DocumentCanvas` (`documentcanvas.cpp:1434,1455,1539`); дорого именно
пробуждение QML на каждый кадр.

Формально после D1 сводки в дереве нет и будить некого, но D3 закрывает
источник со стороны C++: подписчик может появиться снова. Замерено, что вклад
реальный: `FrameStats` без `window` - 22.1% против 24.6% базовых (второй
источник при этом продолжал работать).

### D5. Полоса экспорта рисуется своими руками, а не системным контролом

`Loader` из D1 убирает петлю из простоя, но не из экспорта: пока панель
открыта, анимация Breeze крутится и шумит в вывод. Экспорт - как раз тот
момент, когда процессор нужен делу, а не бесконечной анимации в скрытом слое
контрола, и ошибки в выводе приложения быть не должно.

Поэтому `ProgressBar` в панели экспорта заменяется полосой из двух
прямоугольников: подложка и заполнение шириной `parent.width * exporter.progress`.

Это не обеднение вида: панель и так нарисована целиком вручную - свой цвет
`#242430`, свой радиус, своя рамка, - и системно стилизован в ней ровно один
элемент, который там и выглядит чужеродно. После замены панель становится
однородной.

Альтернативы:

- *Принять как чужой баг и ничего не делать.* Требование о простое выполняется и
  так. Отвергнуто: во время экспорта расход остаётся, а в выводе - поток
  `TypeError`, который будет маскировать наши собственные предупреждения.
- *Задать приложению стиль Qt Quick Controls явно (`QQuickStyle::setStyle`).*
  Обходит баг, но меняет вид всех контролов приложения на всех машинах ради
  одного дефекта в одном из них. Отвергнуто.
- *Чинить Breeze и ждать обновления.* Стоит сделать отдельно и не в этом
  изменении: пользователю нужно работающее приложение сегодня.

### D4. Методика замера уезжает в репозиторий вместе с цифрами

В `PERFORMANCE.md` добавляется раздел о простое: цифры до и после, контроль
пустым окном - и, отдельным подразделом, четыре ловушки замера из «Context».
Сама процедура кладётся скриптом в `tools/`, чтобы её не приходилось
восстанавливать по памяти. Без этого следующий разбор повторит ту же ошибку:
ловушки дают правдоподобный ложный ноль, а не заметную странность.

## Risks / Trade-offs

- **`Loader` меняет вид или поведение в рабочем режиме: индикатор экспорта
  появляется с задержкой, сводка кадров не встаёт на место.** → В задачи входит
  проверка обоих режимов вживую (экспорт до конца; запуск с `UQ_FRAME_LOG`), а
  не только замер простоя.
- **Внутри `Loader` ломаются ссылки по `id` на внешние объекты
  (`exporter`, `frameStats`, `canvas`).** → Из `sourceComponent` они видны:
  область видимости QML лексическая. Проверяется первым же запуском экспорта.
- **`tst_idleframes` окажется нестабильным: фоновая работа выдаст кадр в окно
  замера.** → Порог - ни одного кадра, а не «мало»: у исправного покоя
  промежуточных значений нет, петля даёт сотни. Устаканивание - до первого
  промежутка без кадров, с верхней границей.
- **`tst_idleframes` будет молча пропускаться на CI и перестанет защищать.** →
  Пропуск виден в выводе `ctest` как `SKIP` с причиной; структурный
  `tst_idlepower` при этом идёт всегда.
- **Остаётся третий источник, который сегодня не проявляется.** → После правки
  замер должен давать ноль, а не «мало»: любое ненулевое значение означает, что
  источник ещё есть. Это проверяется задачей замера, а не рассуждением.

## Migration Plan

Отката не требуется: изменение внутреннее, формат заметки и состояние
пользователя не затрагиваются. Ошибочная правка проявится как неработающий
индикатор экспорта или отсутствующая сводка кадров и чинится возвратом
соответствующего блока.

# Передача работы на Galaxy Book

Документ для агента, который продолжает `ink-beauty-pass` на целевом
устройстве. Прочитать целиком до первой команды.

## Где мы

Ветка `ink-beauty-pass`, версия 0.11.0. Всё, что можно было сделать без
устройства, сделано и проверено: код, тесты (26 из 26 в `ctest`), прокси-замеры
на машине разработки. Решения и их причины - в `design.md` (D1-D10), план с
отметками - в `tasks.md`, числа - в `PERFORMANCE.md`.

Машина разработки - не устройство: Sway, Intel Iris Xe, 60 Гц, без пера, без
KWin. Все числа оттуда помечены «прокси-замер на машине разработки» и годятся
только для сравнения сборок между собой. Числа, которые решают, - с устройства:
Samsung Galaxy Book, KDE Plasma на `kwin_wayland`, 120 Гц, перо Wacom
(`WCOM0174:00 2D1F:0230`), dpr 1.75 (проверить: `kscreen-doctor -o`).

## Что осталось

Девять шагов `tasks.md`, все требуют устройства. Подробные команды, критерии и
что делать при провале - в самих шагах; здесь порядок и смысл.

| Шаг | Что | Чем решается |
| --- | --- | --- |
| 14.1 | Собрать 0.11.0 и 0.9.0 для сравнения, набрать плотную страницу `/tmp/dense.pdf` из `~/kb.pdf` | два бинарника, самый большой батч 25-29 МБ |
| 2.15 | Задержка «событие пера → показ» по `wp_presentation`, письмо пером 3 × 30-60 с | таблица в `PERFORMANCE.md`, `foreign stamps 0`, `clock mismatch 0` |
| 14.2 | Журнал перезаливок при письме: мокрый штрих не перезаливает страницу | перезаливки сухого батча - только в кадрах переноса по простою |
| 14.3 | Бюджет кадра при письме: `kb.pdf` и плотная страница, в том числе `UQ_DEMO_STROKE_MS=300` | p99 интервала ≤ 12.6 мс, длинных кадров не больше числа переносов |
| 14.4 | Навигация: сначала число `rebuild: full`, потом кадры | полных перестроек ≤ числа входов страниц в зону удержания; p99 не хуже 0.9.0 |

| 15.9 | `intel_gpu_top` при навигации, `UQ_MSAA=4` против `0` | RCS при 0 не выше, чем при 4 |

Порядок: 14.1, затем 2.15 (пока устройство «холодное» и ничего не мешает),
затем 14.2-14.6, затем 15.7 и 15.9. Прогоны двух сборок чередовать (новая,
старая, новая, старая), батарея, governor `powersave`, как в 14.3.

## Подготовка

```sh
sudo pacman -S --needed qt6-base qt6-declarative qt6-wayland qt6-webengine \
  qt6-shadertools qpdf abseil-cpp wayland wayland-protocols cmake ninja \
  poppler sqlite intel-gpu-tools
git fetch origin && git switch ink-beauty-pass
git submodule update --init
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DUQ_BUILD_STROKE_LAB=ON -DUQ_DIAGNOSTICS=ON
cmake --build build -j$(nproc)
ctest --test-dir build --output-on-failure
QT_QPA_PLATFORM=wayland ./build/tests/tst_inkmaterialgpu
```

Ожидание: `ctest` - 100%, `tst_inkmaterialgpu` - `Totals: 8 passed` на RHI
OpenGL или Vulkan (под `offscreen` этот тест пропускается, поэтому его гонять
руками). Без `wayland-protocols` замер 2.15 молча не собирается: в выводе
`cmake` должна быть строка «замер задержки до показа (wp_presentation)
включён». Без `-DUQ_DIAGNOSTICS=ON` нет `UQ_DEMO_INK`, `UQ_DEMO_NAV`,
`UQ_SCREENSHOT`.

Известные нестабильные тесты, бывшие и до этой работы: `tst_pagescenegraph`
(`quickReturnKeepsPageReady`, под нагрузкой), изредка `tst_idleframes` и
`tst_penonlymode`. Падение одного из них - перезапустить отдельно; если
воспроизводится стабильно - это уже не нестабильность, разбираться.

## Правила записи результатов

- Числа - только из прогонов на устройстве. Никогда не переносить прокси-числа в
  столбцы устройства и не округлять провал до прохода.
- `PERFORMANCE.md`: заменить «не замерено» в таблицах устройства на числа, с
  датой и сборкой (хэш коммита). Прокси-столбцы не трогать.
- `tasks.md`: у шагов 14.1, 14.2, 14.5, 15.7 отметить подпункт «на
  устройстве» и сам шаг; у остальных - сам шаг. Под шагом одной-двумя строками
  записать, что получилось.
- Снимки и журналы складывать в `/tmp/uq-device/`, в репозиторий не класть.
- Коммиты по-русски, как в истории ветки (`git log`); в конце строка
  `Co-Authored-By:` по правилам сессии.

## Решения, которые зависят от замеров

- **2.15, задержка до показа.** Если медиана `oldest` 20 мс и больше, это
  основание для отдельного изменения про предсказатель кончика (`design.md`,
  Non-Goals, вариант `lat-arc-h8-val` из ветки `exp/latency`). В этой ветке его
  не делать - записать число и предложить пользователю.
- **14.2-14.3, кадры при письме.** Если на плотной странице длинных кадров
  больше, чем переносов недавних штрихов в сухой слой, смотреть журнал
  `QSG_RENDERER_DEBUG=render,change` на кадрах-выбросах: какие узлы
  добавляются. Устройство слоёв - `design.md`, D10; константы -
  `src/canvas/documentcanvas.cpp` (`kRecentFlushMs = 700`, `kRecentSlots = 64`,
  `kWetPoolInitialChunks = 8`). Менять константы можно, архитектуру - только с
  пользователем.
- **14.4, навигация.** Вкладыши, уходящие из зоны удержания, дают полную
  перестройку сцены (известное ограничение, D10). Если на `kb.pdf` это
  заметно, записать и предложить пользователю пул узлов вкладышей.
- **14.6, глазами.** Если тонкая линия на устройстве выглядит хуже, чем на
  снимках прокси, проверить dpr и пол толщины (`InkMaterial`,
  `kDefaultMinHalfWidthPx = 0.15` в `src/ink/inkcoverage.h`; `design.md`,
  Open Questions: альтернатива 0.3 px). Если на тугих петлях «e» и «o»
  бахрома складывается (петля бледнеет), прогнать гейт
  `tools/stroke-lab/gate-rho.sh` и вернуться к пользователю: ограничение по
  радиусу кривизны было отменено как раз потому, что на синтетике складки не
  было (`design.md`, D7).
- **14.6, давление.** Если при ровном нажиме видна рябь толщины, снизить
  `kPressureMinCutoff` в `src/ink/strokesampler.cpp` с 12 до 8 Гц (`design.md`,
  D2) и перепроверить тесты `tst_strokesampler`.
- **15.9, MSAA.** Если RCS с `UQ_MSAA=0` выше, чем с 4, или на 15.7 видны
  лестницы, вернуть `kDefaultSamples = 4` в `src/canvas/surfaceformat.cpp`,
  поправить тест `tst_surfaceformat::defaultIsNoMultisampling` и записать
  результат в `design.md`, D8.

## Чего не делать

- Не сливать ветку в `master` и не архивировать изменение openspec: это решает
  пользователь после замеров.
- Не реализовывать отложенное (D6, ограничение по ρ, предсказатель) - только
  записать числа и предложить.
- Не трогать ветки `exp/*`: это прототипы, на которых сняты числа
  `design.md`.
- Не ослаблять критерии гейтов под результат. Провал - записать, разобрать
  причину, вернуться к пользователю.
